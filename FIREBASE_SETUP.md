# Firebase setup

Status: **the Firebase project is set up and the app is linked to it.**
Google sign-in, Firestore and the Realtime Database are live with tested
security rules. **Cloud Functions are written but not deployed**, because the project
is on the free Spark plan and Functions need the Blaze plan. App Check and
Cloud Messaging are not set up yet.

Singapore was chosen because it is the nearest region that offers the
Realtime Database, and keeping Firestore and Functions in the same region
avoids cross-region delays. **A database's location cannot be changed
later.**

Files that connect the app to the project:

- `lib/firebase_options.dart` and `android/app/google-services.json`,
  generated by `flutterfire configure`. The keys in them identify the
  project; they are not secrets. Access is controlled by the security rules.
- `firebase.json` and `.firebaserc`, which tell the Firebase CLI what to
  deploy and where.
- **Missing: `ios/Runner/GoogleService-Info.plist`.** It could not be written
  on Windows. Run `flutterfire configure` again on a Mac before the first iOS
  build.

## Authentication

- **Passengers need no account.** Anyone with the app can see the map, the
  schedule, routes, stops, announcements and live bus positions without
  signing in. This was decided by the project owner on 10 November 2026.
- **Only drivers and transport office staff sign in**, because only they
  write anything: a driver publishes a bus's position, an admin edits routes,
  stops, buses and announcements.
- **Google is the only way to sign in** (owner's decision, 10 November
  2026). There are no passwords, no registration form and no password
  reset. Email and password sign-in is switched off in the project itself,
  so it cannot be used even from outside the app.
- A driver or staff member taps "Sign in with Google" (Profile, Drivers and
  staff) and chooses their Google account. The first time, the app creates
  their profile with no special access. Its stored role is `student`, which
  the app shows as "Passenger" and which can do nothing the public cannot.
- Any Google account can sign in. That is safe, because signing in grants
  nothing until an admin changes the role.
- The support email people see on Google's sign-in screen is the project
  owner's, chosen by the owner.

### Android signing fingerprint

Google sign-in on Android only works for an app signed with a key whose
fingerprint is registered in the Firebase project. Registered so far: the
SHA-1 and SHA-256 of **this computer's debug key**, which also signs the
release builds made here.

- A build made on another computer will fail to sign in until that
  computer's fingerprint is added:
  `firebase apps:android:sha:create <app id> <fingerprint>`, then download
  `google-services.json` again.
- Before publishing, create a proper release key, register its fingerprint
  (and Google Play's app signing fingerprint) and stop signing releases
  with the debug key.

### Roles

A person's role is the `role` field of their document in `users/{uid}`:
`student` (no special access), `driver` or `admin`. Nobody can change their
own role; the rules allow only an admin to do it.

To make someone a driver: they sign in with Google in the app, then an admin
opens Manage people and makes them a driver, and Manage buses to give them a
bus.

The first admin (the project owner's account) was made on 10 November 2026.
A first admin always has to be made from outside the app, because there is
no admin yet to promote anyone:

1. Sign in with Google in the app.
2. Open the Firebase console, Firestore, `users`, and find the document for
   that account.
3. Change `role` from `student` to `admin`.

Or, from this computer, with the Firebase CLI signed in as the project
owner:

```bash
node tools/dev/set_user_role.js bus-tracker-162c0
```

lists the profiles, and adding an email and a role (`student`, `driver` or
`admin`) changes that person's role.

After that, an admin can change other people's `role` and `isActive`. There
is no screen for that in the app yet, so for now it is also done in the
console.

What an admin can do in the app today (Profile tab, Administration): manage
the stops, the schedule, the buses and people's roles. Announcements are
still changed outside the app.

## Firestore

Collections, as in the specification:

| Collection | Fields | Who reads | Who writes |
|---|---|---|---|
| `users/{uid}` | name, email, studentId, role, isActive, createdAt | The owner, admins | The owner (create as student; later name and studentId only), admins (role, isActive) |
| `buses/{busId}` | busNumber, name, registrationNumber, routeId, driverUid, isActive | Everyone | Admins |
| `routes/{routeId}` | name, color, startLocation, endLocation, path, stopIds, isActive | Everyone | Admins |
| `stops/{stopId}` | name, latitude, longitude, description | Everyone | Admins |
| `routeStops/{id}` | routeId, stopId, sequence | Everyone | Admins |
| `trips/{tripId}` | busId, driverUid, routeId, status, startedAt, endedAt | The trip's driver, admins | Cloud Functions only |
| `announcements/{id}` | title, message, createdAt, isActive | Everyone | Admins |
| `timetables/{id}` | group, route, stops, departures, updatedAt | Everyone | Admins |

"Everyone" includes people who are not signed in. Because these documents
are public, **never put anything private in them** (for example a driver's
phone number in a bus document). Profiles and trips are not public.

An admin must be signed in with a profile whose `isActive` is true; a
deactivated admin can no longer write. Everything not listed is closed.

A timetable document is one route for one passenger group (`student`,
`teacher` or `staff`). `stops` is a list of `{bn, en}` names; `departures`
is a list of `{from: {bn, en}, trips: [{time: "HH:mm", vehicles: {bn,
en}}]}`. The rules check the group, the route number, that both lists are
lists of a sane size, and that `updatedAt` is the server's time. They do not
look inside the lists; the app does that, and skips a document it cannot
read.

`routes.path` is a list of `{latitude, longitude}` points rather than an
encoded polyline, so it can be read and edited directly in the console.

## Realtime Database

Used for what changes every few seconds, and for the two notes the tracking
rules need.

| Path | Holds | Who reads | Who writes |
|---|---|---|---|
| `admins/{uid}` | `true` for each admin | That person, admins | Admins (not themselves) |
| `busDrivers/{busId}` | The uid of the bus's driver | Signed-in users | Admins |
| `activeTrips/{busId}` | tripId, driverUid, status, startedAt, routeId | Everyone | The bus's assigned driver; an admin may delete |
| `liveLocations/{busId}` | tripId, driverUid, latitude, longitude, heading, speed, accuracy, updatedAt | Everyone | The driver of that bus's active trip; an admin may delete |

**There are no Cloud Functions in use.** The project is on the free plan, so
these rules decide who may start a trip:

- `admins` and `busDrivers` are copies of what Firestore says, kept because
  the Realtime Database cannot read Firestore. The app writes them whenever
  an admin changes a person or a bus. If they are ever in doubt, rebuild
  them from Firestore:

  ```bash
  node tools/dev/sync_tracking_access.js bus-tracker-162c0 https://bus-tracker-162c0-default-rtdb.asia-southeast1.firebasedatabase.app
  ```

  The first admin had to be recorded this way, because nobody was yet
  allowed to write `admins`.
- A trip can be started only by the driver recorded in
  `busDrivers/{busId}`, in their own name, with the server's time.
- A position is accepted only if all of these hold:
  - the writer is still that bus's assigned driver, and the trip is theirs
    and active;
  - the trip id and driver id in the position match;
  - the coordinates are numbers inside Bangladesh (latitude 20.5 to 26.7,
    longitude 88.0 to 92.7);
  - heading, speed and accuracy, when present, are in a sane range;
  - `updatedAt` is the server's time, not one chosen by the phone;
  - there are no extra fields;
  - at least one second has passed since the bus's previous position.

A driver therefore cannot start a trip on a bus that is not theirs, publish
for another bus, pose as another driver, back-date a position, or flood the
database. Taking a driver off a bus stops their positions being accepted at
once.

Limitations:

- Reading is public, so nobody can be blocked from reading individually.
  App Check (below) is the way to limit reading to the real app.
- **The free plan allows 100 simultaneous connections** to the Realtime
  Database. Every phone showing live buses is one connection.
- These rules trust the `admins` and `busDrivers` copies. If a copy is
  stale, the rules act on the stale value until it is rewritten.
- A deactivated driver is taken off their bus by the app, which is what
  stops them. The rules alone do not know that an account is deactivated.

## Security rule tests

86 tests run both rule sets against the local emulators and pass. They cover
every case above, including: public reading without an account, no writing
of any kind without an account, self-promotion to driver or admin, creating
a profile for someone else, deactivated and profile-less accounts, client
writes to trips, and each way a driver could publish a false position.

```bash
npm --prefix firebase/test install
```

```bash
firebase emulators:exec --only firestore,database --project demo-bu-bus-tracker "npm --prefix firebase/test test"
```

The emulators need Java 21 or newer on the `PATH` (Android Studio's bundled
one works: `C:\Program Files\Android\Android Studio\jbr\bin`).

In the emulator's log, a denied request can appear as "evaluation error ...
false for 'create'". In the version used here that is how a check that came
out false is reported, not a fault in the rules.

## Cloud Functions

Written in TypeScript in `firebase/functions/`, compiled without errors,
**not deployed, not run, and not used**: the app starts and ends trips
through the Realtime Database rules above instead. They are kept for a
later move to the paid plan.

| Function | What it does |
|---|---|
| `startTrip` | Confirms on the server that the caller is an active driver, finds the one active bus assigned to them and its route, claims the bus atomically so two phones cannot start a trip on it, records the trip, and writes `activeTrips/{busId}`. The driver does not choose the bus or route. |
| `endTrip` | Marks the driver's trip ended and removes `activeTrips/{busId}` and `liveLocations/{busId}`. |

If they are deployed later, the `activeTrips` rule should be closed to
drivers again, so that only the functions can start a trip.

### To deploy them

1. In the Firebase console, upgrade the project to the **Blaze** plan. This
   needs a payment card. Blaze includes the same free allowances as Spark,
   and this app's expected use should stay well within them, but it is
   pay-as-you-go beyond that. Setting a budget alert in Google Cloud Billing
   is recommended.
2. Run:

   ```bash
   firebase deploy --only functions
   ```

If you would rather not use Blaze, the alternative is to manage trips with
security rules alone (an admin records which driver has which bus in the
Realtime Database, and the rules let that driver open a trip). It is less
strict than a Cloud Function and departs from the specification, so it has
not been built; say if you want it.

## App Check

Not set up. The functions have a single switch for it
(`ENFORCE_APP_CHECK` in `firebase/functions/src/config.ts`), off for now.
To turn it on later:

1. In the Firebase console, App Check, register the Android app with Play
   Integrity (needs the app's SHA-256 signing fingerprint) and the iOS app
   with DeviceCheck or App Attest.
2. Add `firebase_app_check` to the app and activate it at startup.
3. Watch the App Check metrics until real phones show as verified.
4. Only then enforce it for Firestore, the Realtime Database and Functions.
   Enforcing it earlier would lock every phone out.

## Working without touching the real project

The app can use the local emulators instead of the real project, so testing
never creates real accounts or data:

```bash
firebase emulators:start --only auth,firestore --project bus-tracker-162c0
```

```bash
flutter run --dart-define=FIREBASE_EMULATORS=true
```

On an Android emulator add `--dart-define=FIREBASE_EMULATOR_HOST=10.0.2.2`.
Everything in the emulators is discarded when they stop.
